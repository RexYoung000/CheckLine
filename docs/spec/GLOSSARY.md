# GLOSSARY — 预算线术语表

> AI 协作时，所有设计、开发、文案必须对齐这份术语表。
> 每个术语包含：**正确定义** + **反面例子**（常见误解）。

---

## 一、核心概念

### 预算线（CheckLine）

| 项目 | 内容 |
|------|------|
| 定义 | 用户为自己设的一条消费边界。线内自由花，线外有意识地停下。 |
| 不是什么 | 不是「省钱 App」，不是「抠门工具」，不是「记账软件」。 |
| 误用案例 | 「预算线帮你省钱」❌ →「预算线帮你把钱花在真正想要的事上」✅ |

### 预算（Budget）

| 项目 | 内容 |
|------|------|
| 定义 | 一个「时间周期 + 主题」的消费容器。例：「6 月生活」「京都旅行」。 |
| 数据结构 | `Budget` 实体，包含：名称 / 模板 / 周期类型 / 起止时间 / 总额 / 分类列表 / 超支策略 / 默认心愿 |
| 不是什么 | 不是银行账户，不是真实资金账户，不是存钱罐。 |
| 误用案例 | 把 Budget 理解成「钱包余额」❌ → Budget 是「这段时间这件事能花多少」✅ |

### 预算钱包（Budget Wallet）

| 项目 | 内容 |
|------|------|
| 定义 | 用户界面里的预算容器表达。一个预算钱包对应一个 `Budget`，让用户直观看到每条独立预算边界。 |
| 与预算线关系 | 「预算线」是品牌和心智；「预算钱包」是 UI 结构和用户理解方式。 |
| 使用位置 | 首页横滑卡片、预算列表、新建预算流程、Stitch 原型说明。 |
| 误用案例 | 把预算钱包做成真实账户余额或资金隔离工具 ❌ → 它只是预算容器表达 ✅ |

### 周期类型（Cycle Type）

| 项目 | 内容 |
|------|------|
| 定义 | 预算的时间属性。`repeating`（重复型）到期自动开下一周期；`oneShot`（单次型）到期后归档。 |
| 误用案例 | 把所有预算默认设定为 `repeating` ❌ → 创建时让用户选 ✅ |

## 二、记一笔与预算消耗

### 记一笔（Capture / Record an Expense）

| 项目 | 内容 |
|------|------|
| 定义 | 记录一笔消费行为。不是「记账」，是用户主动标记「我花了这笔」。 |
| 入口 | 手动 / Widget 速记 / 截图识别 / 语音 / 分享扩展 / Shortcuts |
| 不说 | 「记账」「录入流水」「登记支出」→ 说「记一笔」 |

### 预算消耗（Budget Spending）

| 项目 | 内容 |
|------|------|
| 定义 | 一笔消费让预算进度发生变化的行为。不是冷冰冰数字减法，是有动效、有 Haptic 反馈的体感动作。 |
| 数据层 | 通过 `BudgetExpenseBinding.recordedAmount` 反映，不直接改 `Budget.totalAmount`。 |
| 误用案例 | 直接 `budget.remaining -= amount` ❌ → 走 binding 层扣 `recordedAmount`，运行时算 `remaining` ✅ |

### 扣血（Internal Metaphor）

| 项目 | 内容 |
|------|------|
| 定义 | 内部沟通里的动效比喻，用来描述预算条被消费记录影响的体感。 |
| 使用限制 | 只能出现在内部文档、注释或沟通里，不能出现在用户可见界面。 |
| 用户界面替代 | 「记下这笔」「已用」「最近记录」「预算快用完了」。 |

### 归类弹窗（Categorization Sheet）

| 项目 | 内容 |
|------|------|
| 定义 | 记一笔的核心交互界面。用户确认金额 → 勾选归属预算（可多选）→ 选分类 → 记下这笔。 |
| 关键设计 | 预算标签是**平等的多选**，没有「主预算 / 副预算」层级。 |
| 误用案例 | 做「主预算 + 关联预算」两栏 UI ❌ → 做「当前预算标签」+ 「添加其他标签」平等勾选 ✅ |

## 三、多预算关系

### 平等标签（Equal Tags）

| 项目 | 内容 |
|------|------|
| 定义 | 一笔消费归到多个预算时，所有勾选的预算地位平等，没有主从关系。每个被勾选的预算都独立计入。 |
| 数据层 | 一个 Expense ↔ 多个 Budget，通过 `BudgetExpenseBinding` 中间表。 |
| 误用案例 | 设计「主预算」「副预算」概念 ❌ → 所有勾选预算都是平等的 ✅ |

### 关联账（Linked Expense）

| 项目 | 内容 |
|------|------|
| 定义 | 同一笔消费被记到了 ≥ 2 个预算里（同一 ExpenseID，多条 `BudgetExpenseBinding`）。结算时系统识别出来，让用户确认「这笔实际算几次」。 |
| 不是什么 | 不是两笔不同的账，不是重复记账。是同一笔消费在多个预算视角下的投影。 |
| 误用案例 | 结算时把所有关联账按「独立计入」算成两笔 ❌ → 识别同 ExpenseID，让用户选「都算 / 仅算 X」✅ |

### LinkedExpenseDetector

| 项目 | 内容 |
|------|------|
| 定义 | 领域服务。结算时扫描该预算所有 `BudgetExpenseBinding`，找出 ExpenseID 出现 ≥ 2 次的关联账。 |
| 输出 | 关联账列表（待用户确认的 ViewModel） |

## 四、结算

### 结算清单（Settlement Checklist）

| 项目 | 内容 |
|------|------|
| 定义 | 预算结束时展示的总结页。包含：总支出 / 关联账确认 / 最终结余 / 心愿分配。 |
| 双轨触发 | 重复型 → 到期自动弹；单次型 → 到期提醒 + 用户点击触发。 |
| 误用案例 | 单次型预算到期直接归档不弹结算清单 ❌ → 任何预算结束都走结算清单 ✅ |

### 结算高光（Settlement Highlight）

| 项目 | 内容 |
|------|------|
| 定义 | 结算确认后的强仪式感动画。强动画 + 数字骤变 + Haptic + 分享卡片。产品的「情感峰值」之一。 |
| 适用范围 | **任何预算类型**（重复 / 单次），仪式感不能因为类型不同打折。 |
| 误用案例 | 只有重复型预算有结算高光，单次型没有 ❌ → 所有类型一致 ✅ |

## 五、心愿

### 心愿（Wish）

| 项目 | 内容 |
|------|------|
| 定义 | 用户想攒钱达成的目标。独立于预算的实体，与预算是多对一关系。 |
| 数据结构 | `Wish` 实体：名称 / 目标金额 / 图标 / 主题色 / 已累积金额（派生） |
| 不是什么 | 不是「荷包」，不是「存钱目标工具」，不是「购物清单」。 |
| 误用案例 | Wish 内嵌在 Budget 里作为子对象 ❌ → Wish 是独立实体 ✅ |

### 心愿分配（Wish Allocation）

| 项目 | 内容 |
|------|------|
| 定义 | 结算时用户把预算结余分配到心愿的操作。默认选创建预算时预设的心愿，用户可拆分到多个心愿、自定义金额、甚至不转。 |
| 数据层 | `Settlement` → `WishAllocation` → `Wish`。一个 Settlement 可以有多个 WishAllocation。 |
| 关键原则 | **分配权归用户。** 系统不替用户拍板。 |

### 心愿达成（Wish Achievement）

| 项目 | 内容 |
|------|------|
| 定义 | 心愿累积金额 ≥ 目标金额时触发。全屏庆祝动画 + 分享卡片。产品**最大的情感峰值**。 |

---

## 六、状态与控制

### 超支策略（Overrun Strategy）

| 项目 | 内容 |
|------|------|
| 定义 | 预算超过总额时的处理方式。创建预算时由用户选择： |
| | `warnOnly` — 温柔提示「今日预算用完了」，不影响心愿 |
| | `deductFromWish` — 超支金额从默认心愿扣回 |
| 误用案例 | 系统默认选一个超支策略 ❌ → 创建时让用户选 ✅ |

### 预算模式上下文（Budget Context / Mode）

| 项目 | 内容 |
|------|------|
| 定义 | 用户当前主要在哪个预算下活动。影响：首屏 C 位显示、记一笔默认勾选。 |
| 切换方式 | 用户在主屏切换预算，或进入某个预算的详情页。 |
| 误用案例 | 记一笔永远默认上一次选的预算但用户已切换到别的预算 ❌ |

## 七、数据模型专用

### BudgetExpenseBinding

| 项目 | 内容 |
|------|------|
| 定义 | Budget 与 Expense 的多对多中间表。一条 binding 代表「一笔消费在某个预算下的计入」。 |
| 关键字段 | `recordedAmount`（计入金额）、`finalAttribution`（结算时的归属决策） |
| 误用案例 | 直接在 Expense 上设 `budgetId` 字段做一对多 ❌ → 走 Binding 中间表 ✅ |

### 派生属性（Derived Property）

| 项目 | 内容 |
|------|------|
| 定义 | 不持久化到数据库，运行时通过纯函数计算的属性。如 `Budget.remaining` = `totalAmount - spent`。 |
| 为什么 | 避免数据不一致。持久化 `remaining` 会在并发记账时出错。 |
| 误用案例 | 建表时加一个 `remaining` 列并手动维护 ❌ → 只存 `totalAmount`，`remaining` 运行时算 ✅ |

## 八、录入入口

| 术语 | 定义 |
|------|------|
| **Widget 速记** | iOS 锁屏 Widget，一点直进归类弹窗，全程不打开主 App |
| **截图识别** | Photos + Vision OCR，检测到支付截图 → 自动填金额 → 弹归类弹窗 |
| **语音录入** | Speech + 端侧 AI 解析，「打车 38」一句话自动拆金额+分类 |
| **分享扩展** | 长按支付宝/微信支付通知 → 分享到 CheckLine → 弹归类弹窗 |

## 九、使用纪律

- 代码中的变量名、类名、注释**必须对齐这份术语表**
- 新概念诞生时，先加进这份表，再写代码
- AI 协作时若对某个术语有歧义，回到这里查「误用案例」列
- 术语表 ≠ 用户界面文案。用户界面文案遵循 PRODUCT.md 第六节文案原则
