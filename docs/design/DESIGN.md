# DESIGN - CheckLine 当前设计事实来源

本文记录 CheckLine 的设计原则、体验底线、当前设计方案和探索边界，是当前视觉与交互的唯一事实来源。

“唯一事实来源”表示已经确认的设计决定统一在这里维护，不表示文档中的每个颜色、尺寸或组件形式都是永久强规则。产品范围与业务规则以上位的 `PRODUCT.md`、`PRD.md` 和 `FEATURE-LOOP.md` 为准，本文不能自行扩大产品范围。

## 阅读方式

本文按四个层级管理设计内容：

| 层级 | 作用 | 执行方式 |
|---|---|---|
| 设计原则 | 判断产品应该如何被理解和感受 | 不得违背 |
| 体验底线 | 定义用户必须获得的可靠结果 | 必须验收，实现方式不限 |
| 当前设计方案 | 记录当前采用的视觉与交互基线 | 开发默认遵循，可以经设计确认迭代 |
| 探索与参考 | 保存待验证方向、外部案例和历史依据 | 不能直接作为开发或验收要求 |

开发或 AI 不能以实现便利、系统默认外观或个人偏好自行改变当前方案。长文本换行、点击热区扩展、键盘避让等不改变产品含义的小型适配可以直接完成；会改变信息层级、导航、品牌视觉或核心流程的调整，需要先完成设计确认并更新本文。

## 一、设计原则

### 1.1 看见自己划定的消费边界

CheckLine 不是帮助用户管理总资产，也不以建立完整流水为目标。它帮助用户在消费前、消费中和预算结束后，看见并理解自己为一段时间、一件事情主动划定的消费边界。

- 预算的本体是“时间 + 主题 + 金额边界”，不是真实账户或资金容器。
- 用户最重要的问题是“这件事我还愿意花多少”，而不是“我一共有多少钱”。
- 消费记录用于更新和解释预算状态，不追求专业记账软件的字段完整度。
- 统计用于回看边界是否适合用户，不扩张成商业财务分析。
- 结余不天然代表成功，超出也不天然代表失败。
- 产品不评价某笔消费是否值得，也不教育用户应该省钱。

界面因此优先表达当前预算、时间范围、已用、还能花、相关消费和阶段回看，不以总资产、账户余额、银行卡或净资产作为核心信息。

### 1.2 清晰表达边界，同时尊重用户

CheckLine 的品牌态度是克制、温柔、有边界、可信。

- **克制**：信息和反馈不过度争夺注意力，不为了显得功能丰富而堆叠入口。它不是浅色、极简或系统默认外观的同义词。
- **温柔**：如实说明状态，但不评价用户、不制造羞耻，也不通过焦虑推动行动。它不是幼态化、可爱化或回避真实结果。
- **有边界**：产品知道自己不该替用户做什么，也让每条预算的范围和状态清楚可见。
- **可信**：金额、归属、状态和操作影响稳定明确，不能为了视觉效果牺牲理解。

视觉可以使用鲜明色彩、自定义字体、原创构图和品牌动效，只要仍然服务于清晰、尊重和边界感。不得为了原生感抹掉品牌个性，也不得为了视觉个性让金额、状态或操作难以理解。

### 1.3 用户拥有有财务含义的决定权

系统可以帮助用户计算、预填、提醒和提出建议，但凡会改变一笔钱的含义、归属或最终结果，都不能在用户不知情的情况下替用户决定。

系统可以：

- 根据当前上下文预选预算。
- 记住最近使用的分类或操作偏好。
- 自动计算已用、还能花、进度、超出金额和结余。
- 识别一笔消费可能关联多个预算。
- 提供推荐选项、默认值和批量处理能力。
- 对可安全恢复的轻量操作提供撤销。

系统不能：

- 静默决定或移动一笔消费的预算归属。
- 为避免超出而自动把消费转到其他预算。
- 自动修改预算金额或分类额度。
- 自动分配结余。
- 把推测结果伪装成用户已经确认的事实。
- 在后台改变历史记录的金额、归属或结算结果。

不改变金钱含义的便利操作可以直接完成；可逆的小影响操作可以先执行并提供撤销；会改变多个预算结果或不可逆的操作需要先说明影响并由用户确认。尊重决定权不等于让用户手动完成每个步骤，也不等于机械增加确认弹窗。

### 1.4 多预算独立且平等

- 每个预算都有独立周期、总额、分类、记录与结算。
- 一笔消费可以同时归属多个预算，所有预算标签平等。
- 不建立主预算、副预算或全局总额封顶。
- 当前正在查看和操作哪个预算必须清楚。
- 消费影响哪些预算以及每个预算如何变化必须可以理解。

“预算钱包”或预算卡片可以继续作为帮助用户理解独立预算的表达，但不是永久固定的视觉形式，也不能让用户误以为其中存放真实资金。

### 1.5 产品语言边界

稳定的核心概念：

- 预算线 / CheckLine
- 预算、预算钱包
- 记一笔
- 已用、还能花、最近记录、结余
- 这笔归到哪些预算

禁止造成错误产品心智的表达：

- 扣血
- 记账
- 主预算 / 副预算
- 总资产 / 账户余额
- AI 智能记账建议
- 当前版本中的转到心愿 / 离心愿近了

“扣血”只能用于内部讨论动效感受，不能进入用户可见字符串、无障碍内容或通知。具体按钮、状态和辅助文案可以根据上下文及中英文表达自然迭代，只要不改变产品含义。

## 二、体验底线

体验底线约束用户最终获得的结果，不指定必须采用的控件、字号、布局或视觉风格。Apple HIG、WCAG、模拟器和自动化检查都是发现问题的参考工具，不拥有 CheckLine 的设计决策权。

### 2.1 看得清

- 关键金额、预算名称、状态、日期和操作在当前支持设备上保持可读。
- 系统文字缩放、长中文、英文、长金额和本地化日期不能造成内容重叠或核心含义丢失。
- 金额不得因静默截断而变成错误数字；空间不足时使用布局变化、换行或受控缩放。
- 辅助文字不能为了视觉气质小到难以阅读。
- 背景、图片和装饰可以延伸到屏幕边缘，关键内容不能被状态栏、设备切口、Home Indicator、键盘或底部导航遮挡。

CheckLine 自主定义字体、字号、字重、行高和数字风格。系统语义字号是实现选项，不是视觉强制。

### 2.2 点得到且不易误触

- 高频和关键操作容易触达，不能只依赖隐藏手势。
- 相邻操作的有效点击区域不能互相抢占或造成明显误触。
- 危险操作与日常操作保持足够的空间和语义区分。
- 44 x 44pt 是点击可靠性的默认验收参考，不是控件视觉必须呈现的尺寸。
- Chip、图标或文字按钮可以视觉更小，通过合理热区保证可靠点击。

最终以模拟器和真机中的实际操作为准。

### 2.3 看得懂

- 用户能判断当前选中的预算、分类、日期和筛选条件。
- 操作成功、失败、进行中或尚未生效都有清楚反馈。
- 金额为什么变化、变化影响哪些预算以及共享消费仍归属哪里必须可以理解。
- 选中态不依赖单一颜色，可以结合文字、图标、形状、位置或动效。
- 核心任务和信息归属不能被系统默认容器拆散成难以理解的关系。

### 2.4 能纠错

- 可逆的小影响操作优先提供撤销，不用确认疲劳代替安全。
- 不可逆或影响多个预算的操作提前说明对象、范围和结果。
- 切换预算、分类或弹窗状态时，已经输入的金额与备注不能意外丢失。
- 删除共享消费时，默认只移除当前预算归属；只有用户明确选择后才从所有预算删除。
- 删除预算遇到共享消费时，需要逐笔说明仍关联的预算，默认不勾选全局删除。
- 当前版本没有回收站，经过明确确认的永久删除不能承诺可以恢复。

### 2.5 可访问

- 仅有图标的操作必须让辅助技术理解真实用途。
- 金额需要带单位和上下文，不能只朗读缺少含义的数字。
- 预算状态和进度不能只依赖视觉图形。
- 装饰内容不干扰阅读顺序，焦点顺序与任务顺序一致。
- 自定义组件不能破坏 VoiceOver、焦点、键盘和系统辅助能力。
- 开启减少动态效果后，核心信息和流程仍然完整。

无障碍要求的是等价、完整且不混乱的任务体验，不机械要求每个视觉元素逐一标注。可以把相关信息组合成更自然、完整的朗读内容。

### 2.6 真实状态必须完整

当前功能需要覆盖与其风险相匹配的状态：

| 类型 | 必须回答的问题 |
|---|---|
| 空状态 | 当前为什么没有内容，用户下一步能做什么 |
| 输入状态 | 内容是否有效，切换上下文是否保留输入 |
| 保存 / 计算 | 系统是否正在处理，结果何时生效 |
| 成功 | 哪项操作已经完成，哪些数据发生变化 |
| 失败 | 发生了什么，用户如何继续或恢复 |
| 边界状态 | 接近或越过预算线后真实状态是什么 |
| 危险操作 | 会影响哪些预算、记录和历史结果 |

当前阶段不存在的能力不提前制造界面状态。例如 MVP 尚未启用 iCloud 时，不把同步错误作为当前验收内容。

### 2.7 动效与触感

动效用于解释预算状态如何变化，让用户感受到操作与结果之间的关系；不用于评价消费，也不通过刺激性反馈制造依赖。

- 动画时长、弹簧参数、转场和触感形式不设为永久强规则。
- 记一笔后可以通过金额、预算线或明细的连续变化解释影响。
- 超出预算不使用惩罚性的强震动、失败晃动或破裂效果。
- 结算可以有阶段性情绪表达，但不把“结余更多”包装成更成功。
- 动效不能阻碍操作、遮挡信息或让用户等待核心结果。
- 无动效和减少动态效果时，用户仍能理解状态变化。

### 2.8 平台与设备

- iPhone、iPad 和未来 macOS 共享产品心智、业务规则、数据关系和品牌核心。
- 导航、布局、输入方式和空间组织按各平台真实场景分别设计。
- iPad 不只是把 iPhone 页面等比例拉宽。
- 尚未进入当前路线图阶段的平台不提前固定侧栏、内容宽度、弹窗或快捷入口。
- SwiftUI 是实现框架，不是视觉规范。只有在满足用户理解、产品设计和交互可靠性的前提下，才优先复用系统能力。

### 2.9 验收维度

前端设计按四个维度验收：

1. **理念一致**：是否表达消费边界、尊重用户决定权并符合品牌态度。
2. **任务成立**：用户能否完成创建预算、记一笔、查看状态、回看和结算。
3. **视觉成立**：信息层级、色彩、排版、动效和品牌感是否达到预期，由 Rex 在模拟器或真机中最终确认。
4. **体验底线成立**：不同设备、语言、文字缩放、键盘、VoiceOver 和减少动态效果等场景下是否仍可用。

自动化检查不能替代真实视觉判断，视觉满意也不能替代任务和无障碍验证。

## 三、当前设计方案

本章记录 2026-07-28 的当前基线。开发默认按此实现，但这里的颜色、尺寸、组件和导航形式都可以在新的完整设计判断后调整，不属于永久产品规则。

### 3.1 当前状态

- 当前启动页是使用内存示例数据的 SwiftUI 体验样机。
- 样机用于验证四个主入口、预算钱包、记一笔、统计日历、结算和删除流程。
- 最终品牌视觉尚未定稿，正式 SwiftData MVP UI 尚未完成。
- 当前方案不要求因本次规则调整立即重做；先继续支持正式数据层和领域服务实装。

### 3.2 当前视觉基线

当前继续使用“浅色预算钱包”作为可验证基线：

- 浅灰页面背景与白色内容表面。
- 蓝色作为当前主操作和选中态主色。
- 预算钱包或预算卡片表达独立预算。
- 大金额、预算状态和相关记录形成主要信息层级。
- 分类、明细和设置使用可扫读的分组结构。
- 边框、低强度阴影和适度圆角区分内容表面。

这些都是当前方案，不等于 CheckLine 必须长期浅色、白卡、蓝色或圆角化。品牌可以在后续完整视觉验证中采用其他配色、字体、材质、构图和动效。

### 3.3 当前默认 Token

Token 用于让当前实现保持一致并支持集中迭代。代码优先引用语义 Token，不在各页面散落无含义的具体值。调整 Token 需要同步本文，但不需要证明新值符合旧方案。

#### 颜色

| 语义 | 当前默认值 | 当前用途 |
|---|---|---|
| `canvas` | `#F6F6F8` | 页面背景 |
| `surface` | `#FFFFFF` | 主要内容表面 |
| `surfaceMuted` | `#EEF2F7` | 次级表面 |
| `brandPrimary` | `#135BEC` | 当前主操作与选中态 |
| `textPrimary` | `#0D121B` | 主要文字 |
| `textSecondary` | `#64748B` | 辅助文字 |
| `divider` | `#E5E7EB` | 分隔与弱边界 |

当前不固定红、黄、绿与失败、提醒、成功之间的映射。预算接近或越过边界的含义由文案、数字、图形和结构共同表达。真正具有破坏性的删除操作可以使用独立危险语义。

#### 排版

| 语义 | 当前默认 | 用途 |
|---|---|---|
| `amountDisplay` | 36-40pt / bold | 首页与详情的核心金额 |
| `pageTitle` | 28pt / bold | 页面标题 |
| `sectionTitle` | 20-22pt / semibold | 主要区块 |
| `itemTitle` | 17pt / semibold | 卡片与列表标题 |
| `body` | 15-17pt / regular | 正文与主要说明 |
| `supporting` | 12-14pt / regular | 标签与辅助信息 |

金额当前使用圆角或等宽数字并保持对齐。固定字号、系统语义字号和缩放方式都只是实现选项；最终以信息层级和适配后的可读结果为准。

#### 间距、形状与动效

| 类别 | 当前默认 |
|---|---|
| 基础间距 | 4 / 8 / 16 / 24 / 32pt |
| 页面水平留白 | 约 20pt，按设备与构图调整 |
| 小型控件圆角 | 8-12pt |
| 标准表面圆角 | 16-18pt |
| 钱包主表面圆角 | 约 24pt |
| 微交互 | 约 150ms |
| 状态与内容变化 | 约 300ms |

以上数值帮助当前样机保持节奏，不是 Apple 要求，也不是视觉验收的硬性参数。

### 3.4 当前信息架构

体验样机当前使用四个主入口：

| 入口 | 当前职责 |
|---|---|
| 首页 | 当前预算状态、预算切换、分类与最近记录 |
| 预算 | 全部预算、预算详情、新建与编辑 |
| 统计 | 月度回看、预算比较、分类分析、消费记录日历 |
| 我的 | 设置、教程、隐私与关于 |

「记一笔」当前不占独立 Tab，在首页和关键页面提供明显主入口。四 Tab、入口位置和具体导航控件属于当前方案；核心任务必须保持容易发现，但后续可以经设计确认调整导航形式。

心愿不进入当前版本导航。

### 3.5 当前页面方案

#### 首页

首页首先回答当前在看哪条预算线、这段时间已经用了多少、还能花多少以及最近发生了什么。

当前使用：

- 横向预算钱包或卡片切换当前预算。
- 当前卡片停靠后同步更新分页、分类、日期和最近记录。
- 核心金额作为最高层级，预算名称、周期和摘要逐级后退。
- 当前预算摘要与相关分类、记录保持空间和数据连续。
- 一个明确的「记一笔」主操作。

横向切换、卡片、分页点和主操作外形都可以调整，但不能出现当前预算与下方数据不一致，也不能把同一工作流拆成难以理解的孤立区域。

#### 预算与预算详情

- 预算列表区分进行中、待结算和可回看的状态。
- 每个预算清楚显示名称、周期、已用、还能花或结算状态。
- 详情回答预算边界、当前状态、主要分类、最近记录和是否需要结算。
- 编辑、管理记录和删除预算容易找到，但危险操作不与日常主操作混淆。

删除交互遵循 `PRD.md` 的数据范围规则。共享记录默认保留其他预算归属，界面使用用户语言说明影响，不展示 binding、级联删除等实现术语。

#### 记一笔

当前流程：

1. 输入金额。
2. 选择一个或多个平等预算。
3. 选择分类。
4. 添加可选备注。
5. 确认记下。

当前上下文可以预选预算。切换预算或分类时保留金额和备注；键盘出现后，金额输入与主要操作仍然可用。保存后清楚呈现哪些预算发生变化，并为适合撤销的操作提供恢复机会。

“记下这笔”是当前按钮文案，不限制未来在不同上下文中使用同义且自然的表达。

#### 统计与消费记录日历

- 统计只服务预算边界和消费回看，不做复杂财务报表。
- 支持查看全部预算或单个预算。
- 展示月度概览、预算与实际、分类分析和消费记录日历。
- 筛选变化后，图表、日期标记和当天记录同步更新。
- 日期记录显示所属预算，避免多预算上下文丢失。

柱状图、环形图、日历控件和页面位置都属于设计方案，不是产品固定形式。

#### 我的 / 设置

- 展示当前预算摘要和中性的使用信息，不把少花或结余包装成成绩。
- 提供预算设置、记录管理、教程、隐私、反馈和版本等当前真实入口。
- 后续能力只有进入路线图阶段后才可以承诺可用；样机如预览 iCloud、导出或通知入口，必须明确标注为未来能力，不能伪装成已经实现。
- 当前使用清晰、可扫读的分组结构，具体容器形式可以调整。

#### 结算

- 展示预算总额、总支出、结余和预算周期。
- 存在共享消费时逐笔确认最终归属。
- 每个选择有明确选中态，完成前可以理解它会怎样影响相关预算。
- 进行中预算只预览结果，待结算预算才能正式完成结算。
- 当前版本不出现转到心愿。

结算反馈用于阶段性回看和确认，不将结余多少评价为成功或失败。

### 3.6 当前共享组件语义

相同产品语义和交互行为尽量复用同一组件，但组件外观、尺寸和场景变体可以持续调整。

| 组件语义 | 必须保持一致的内容 | 当前表现 |
|---|---|---|
| 预算上下文 | 当前预算明确，多预算平等 | 钱包卡片、分页与选中边框 |
| 边界进度 | 计算口径一致，状态可理解 | 线性进度与金额 |
| 预算选择 | 平等多选，选中清楚 | 标签 / Chip |
| 分类选择 | 当前分类清楚，切换不丢输入 | Pill / Picker |
| 记一笔入口 | 操作含义一致且容易发现 | 底部主按钮或工具栏入口 |
| 操作反馈 | 结果明确，可逆操作可恢复 | Toast、数字变化与触感 |
| 空状态 | 解释当前状态与下一步 | 标题、说明与行动入口 |

如果已有组件影响用户理解，可以重构或替换；不能因为代码已经抽象出来就成为设计负担。

### 3.7 当前样机已验证
