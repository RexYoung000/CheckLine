## 一、设计原则

### 1.1 看见自己划定的消费边界

CheckLine 不是帮助用户管理总资产，也不以建立完整流水为目标。它帮助用户在消费前、消费中和预算结束后，看见并理解自己为一段时间、一件事情主动划定的消费边界。

- 预算的本体是“时间 + 主题 + 金额边界”，不是真实账户或资金容器。
- 用户最重要的问题是“这件事我还愿意花多少”，而不是“我一共有多少钱”。
- 消费记录用于更新和解释预算状态，不追求专业记账软件的字段完整度。
- 统计用于回看边界是否适合用户，不扩张成商业财务分析。
- 结余不天然代表成功，超出也不天然代表失败。
- 产品不评价某笔消费是否值得，也不教育用户应该省钱。

界面因此优先表达当前预算、时间范围、已用、还能花、相关消费和阶段回看，不以总资产、账户余额、银行卡或净资产作为核心信息。

### 1.2 清晰表达边界，同时尊重用户

CheckLine 的品牌态度是克制、温柔、有边界、可信。

- **克制**：信息和反馈不过度争夺注意力，不为了显得功能丰富而堆叠入口。它不是浅色、极简或系统默认外观的同义词。
- **温柔**：如实说明状态，但不评价用户、不制造羞耻，也不通过焦虑推动行动。它不是幼态化、可爱化或回避真实结果。
- **有边界**：产品知道自己不该替用户做什么，也让每条预算的范围和状态清楚可见。
- **可信**：金额、归属、状态和操作影响稳定明确，不能为了视觉效果牺牲理解。

视觉可以使用鲜明色彩、自定义字体、原创构图和品牌动效，只要仍然服务于清晰、尊重和边界感。不得为了原生感抹掉品牌个性，也不得为了视觉个性让金额、状态或操作难以理解。

### 1.3 用户拥有有财务含义的决定权

系统可以帮助用户计算、预填、提醒和提出建议，但凡会改变一笔钱的含义、归属或最终结果，都不能在用户不知情的情况下替用户决定。

系统可以：

- 根据当前上下文推荐唯一结算预算卡和标签。
- 对信息明确、低风险的单笔记录直接执行，并立即提供撤销。
- 低置信归属暂计最可能预算卡，但明确拆出待确认金额。
- 自动计算已用、还能花、越线、结余、钱包余额和待恢复差额。
- 提出可读匹配规则和批量处理建议，由用户决定是否应用。

系统不能：

- 把不确定归属伪装成用户已经确认的事实。
- 为避免越线而自动把消费转到其他预算卡。
- 未经确认修改预算金额、周期、多个历史记录或结算结果。
- 绕过用户确认执行结算、心愿兑现、钱包扣减或追溯修正。
- 让 Agent 自由生成余额或替用户制定生活方式。

可逆、低风险且高把握的动作可以先执行并提供撤销；归属不确定时先确认；有重大金额影响或不可逆的操作必须先说明影响并由用户确认。尊重决定权不等于让用户手动完成每个步骤，也不等于机械增加确认弹窗。

### 1.4 多张预算卡独立，一笔消费只结算一次

- 每张预算卡都有独立用途、额度、周期、记录与结算。
- 一笔消费最多影响一张结算预算卡，也可以暂时未纳入预算。
- 餐饮、人情、聚会等多重含义用标签表达，标签不重复扣减金额。
- 不建立主预算、副预算、关联预算或全局总额封顶。
- 当前正在查看和操作哪张预算卡必须清楚。
- 待确认金额、未纳入预算和最终金额影响必须可理解。

“预算钱包”或预算卡片可以继续作为视觉表达，但不是永久固定形式，也不能让用户误以为其中存放真实资金。

### 1.5 产品语言边界

稳定的核心概念：

- 预算线 / CheckLine
- 预算卡、预算钱包
- 记一笔
- 已用、还能花、待确认、未纳入预算、数据覆盖
- 结算、心愿钱包、待恢复差额、心愿兑现
- 这笔归到哪张预算卡 / 这笔有哪些标签

禁止造成错误产品心智的表达：

- 扣血
- 记账
- 主预算 / 副预算 / 关联预算
- 总资产 / 账户余额
- AI 自动替你管钱
- 把心愿钱包描述为真实资金或绝对安全可花额度

“扣血”只能用于内部讨论动效感受，不能进入用户可见字符串、无障碍内容或通知。具体按钮、状态和辅助文案可以根据上下文及中英文表达自然迭代，只要不改变产品含义。

## 二、体验底线

体验底线约束用户最终获得的结果，不指定必须采用的控件、字号、布局或视觉风格。Apple HIG、WCAG、模拟器和自动化检查都是发现问题的参考工具，不拥有 CheckLine 的设计决策权。

### 2.1 看得清

- 关键金额、预算名称、状态、日期和操作在当前支持设备上保持可读。
- 系统文字缩放、长中文、英文、长金额和本地化日期不能造成内容重叠或核心含义丢失。
- 金额不得因静默截断而变成错误数字；空间不足时使用布局变化、换行或受控缩放。
- 辅助文字不能为了视觉气质小到难以阅读。
- 背景、图片和装饰可以延伸到屏幕边缘，关键内容不能被状态栏、设备切口、Home Indicator、键盘或底部导航遮挡。

CheckLine 自主定义字体、字号、字重、行高和数字风格。系统语义字号是实现选项，不是视觉强制。

### 2.2 点得到且不易误触

- 高频和关键操作容易触达，不能只依赖隐藏手势。
- 相邻操作的有效点击区域不能互相抢占或造成明显误触。
- 危险操作与日常操作保持足够的空间和语义区分。
- 44 x 44pt 是点击可靠性的默认验收参考，不是控件视觉必须呈现的尺寸。
- Chip、图标或文字按钮可以视觉更小，通过合理热区保证可靠点击。

最终以模拟器和真机中的实际操作为准。

### 2.3 看得懂

- 用户能判断当前预算卡、周期、标签和数据来源覆盖。
- 操作成功、失败、进行中、待确认或尚未生效都有清楚反馈。
- 金额为什么变化、是否包含待确认金额、会怎样影响结算与心愿钱包必须可以理解。
- 选中态和风险状态不依赖单一颜色，可以结合文字、图标、形状、位置或动效。
- 核心任务和信息归属不能被系统默认容器拆散成难以理解的关系。

### 2.4 能纠错

- 可逆的低风险操作优先提供撤销，不用确认疲劳代替安全。
- 删除、批量修改、结算、钱包和历史追溯提前说明对象、范围和金额结果。
- 切换预算卡、标签或 Agent 面板状态时，已经输入的金额与备注不能意外丢失。
- 删除已参与结算或心愿钱包的交易时，先展示追溯影响，再由用户确认。
- 迟到交易和退款必须定位原周期，不静默塞入当前周期。
- 当前是否提供回收站尚未重新确认，不提前承诺永久删除后的恢复能力。

### 2.5 可访问

- 仅有图标的操作必须让辅助技术理解真实用途。
- 金额需要带单位和上下文，不能只朗读缺少含义的数字。
- 预算状态和进度不能只依赖视觉图形。
- 装饰内容不干扰阅读顺序，焦点顺序与任务顺序一致。
- 自定义组件不能破坏 VoiceOver、焦点、键盘和系统辅助能力。
- 开启减少动态效果后，核心信息和流程仍然完整。

无障碍要求的是等价、完整且不混乱的任务体验，不机械要求每个视觉元素逐一标注。可以把相关信息组合成更自然、完整的朗读内容。

### 2.6 真实状态必须完整

当前功能需要覆盖与其风险相匹配的状态：

| 类型 | 必须回答的问题 |
|---|---|
| 空状态 | 当前为什么没有内容，用户下一步能做什么 |
| 输入状态 | 内容是否有效，切换上下文是否保留输入 |
| 保存 / 计算 | 系统是否正在处理，结果何时生效 |
| 成功 | 哪项操作已经完成，哪些数据发生变化 |
| 失败 | 发生了什么，用户如何继续或恢复 |
| 边界状态 | 接近或越过预算线后真实状态是什么 |
| 危险操作 | 会影响哪些预算、记录和历史结果 |

当前阶段不存在的能力不提前制造界面状态。例如 MVP 尚未启用 iCloud 时，不把同步错误作为当前验收内容。

### 2.7 动效与触感

动效用于解释预算状态如何变化，让用户感受到操作与结果之间的关系；不用于评价消费，也不通过刺激性反馈制造依赖。

- 动画时长、弹簧参数、转场和触感形式不设为永久强规则。
- 记一笔后可以通过金额、预算线或明细的连续变化解释影响。
- 超出预算不使用惩罚性的强震动、失败晃动或破裂效果。
- 结算可以有阶段性情绪表达，但不把“结余更多”包装成更成功。
- 动效不能阻碍操作、遮挡信息或让用户等待核心结果。
- 无动效和减少动态效果时，用户仍能理解状态变化。

### 2.8 平台与设备

- iPhone、iPad 和未来 macOS 共享产品心智、业务规则、数据关系和品牌核心。
- 导航、布局、输入方式和空间组织按各平台真实场景分别设计。
- iPad 不只是把 iPhone 页面等比例拉宽。
- 尚未进入当前路线图阶段的平台不提前固定侧栏、内容宽度、弹窗或快捷入口。
- SwiftUI 是实现框架，不是视觉规范。只有在满足用户理解、产品设计和交互可靠性的前提下，才优先复用系统能力。

### 2.9 验收维度

前端设计按四个维度验收：

1. **理念一致**：是否表达消费边界、尊重用户决定权并符合品牌态度。
2. **任务成立**：用户能否完成创建预算、记一笔、查看状态、回看和结算。
3. **视觉成立**：信息层级、色彩、排版、动效和品牌感是否达到预期，由 Rex 在模拟器或真机中最终确认。
4. **体验底线成立**：不同设备、语言、文字缩放、键盘、VoiceOver 和减少动态效果等场景下是否仍可用。

自动化检查不能替代真实视觉判断，视觉满意也不能替代任务和无障碍验证。

## 三、最新已确认框架与历史样机

2026-08-10 之后，旧样机不再是开发默认方案。新 V1 先完成交互形态收敛，再重做正式 UI；本章保留旧 Token、页面和验证记录，只用于复用视觉经验与追溯过程。

### 3.1 最新已确认交互框架

本章只锁信息架构、必须出现的字段和升级条件。不锁卡片密度、配色、字号、圆角和动效；那些在 M4 用真实页面和目标视口验收。

不能从旧四 Tab 样机、右下角悬浮「文本/语音」或「单卡大号剩余」自动继承实现。对照见 3.4 / 3.5。

#### 3.1.1 首页信息层级

首页主体是预算状态，不是聊天窗口，也不是单张卡的剩余金额作为全屏唯一强焦点。

从上到下：

1. **顶部处理区**：待确认交易、未纳入预算、数据覆盖缺口、可能或确定的边界风险。无事项时收起，不占主视觉。
2. **预算卡列表**：按用户 `sortIndex` 固定顺序展示全部进行中的卡，不因风险每天自动跳位。
3. **每张卡必须能读到**：名称、周期、已用、还能花、单独列出的待确认金额、周期进度。待确认金额不能混进确定剩余；只触发「可能接近或越线」，不能形成确定越线结论。
4. **底部常驻 Agent**：文字、语音、图片同一入口，不遮挡处理区和卡片上的关键金额。

心愿钱包余额不是首页第一信息。可在首页以次级摘要出现（见 3.1.2），但不能压过预算卡状态。

无截止日期的一次性预算只展示剩余额度，不展示按速度推算的时间风险。

#### 3.1.2 主导航

根界面就是首页，不再使用四个并列 Tab。统计日历不作为 V1 一级入口。

| 从哪里 | 到哪里 |
|--------|--------|
| 点一张预算卡 | 该卡详情与属于它的记录 |
| 点处理区条目 | 对应的待确认、未纳入、覆盖缺口或风险说明 |
| 首页次级入口：心愿 | 唯一钱包摘要（余额 + 待恢复差额）→ 心愿清单与兑现 |
| 首页次级入口：设置 | 数据来源、隐私与可跳过/断开/补连 |
| 底部常驻 Agent | 任务面板；不是 Tab |

记录、心愿、设置都必须能从首页到达。Agent 不是主导航项，是底部常驻控件。

首次引导顺序不变：创建第一张预算卡 → 可选心愿 → 可选数据来源 → 可选近期账单 → 首页。

#### 3.1.3 Agent 底部任务面板

三态，由低到高：

```text
收起入口
  → 底部任务面板（首页上方，不离开首页）
    → 全屏确认
```

| 情况 | 落在哪一层 |
|------|------------|
| 信息明确的低风险单笔记一笔；查询已用、剩余、覆盖 | 面板内完成；写入后立即提供撤销 |
| 归属不确定、图片包含多笔、关键字段缺失 | 面板内先展示结构化结果，用户确认后再执行 |
| 调额度、改周期、删除、批量修改、结算、钱包变化、心愿兑现、追溯修正 | 升全屏，先展示金额影响再确认 |

文字、语音、图片进入同一面板，不拆成多个产品入口。语音或图片权限被拒绝时回退文字，不反复弹窗。切换预算卡或面板状态时，已输入的金额和备注不得丢失。

Agent 不算余额、结余或钱包数字；面板和全屏展示的金额必须来自确定性领域服务。

#### 3.1.4 结算与心愿确认页

结算必须走全屏确认。页面必须出现：

- 本周期额度；
- 已确认支出；
- 结余或越线金额；
- 仍待确认的金额或笔数；
- 各数据来源最后覆盖时间；
- 可能缺失的数据；
- 用户是否明确接受仍可能不完整的数据；
- 对唯一心愿钱包和待恢复差额的影响预览（结余先补差额再进钱包；越线先扣钱包，不足形成待恢复差额）。

用户确认后才提交。不能静默结算，也不能要求传统强制对账。

心愿兑现必须走全屏确认。页面必须出现：

- 心愿名称；
- 实际成交金额（不是目标参考价）；
- 扣减后的钱包余额；
- 钱包不足时不能把该笔标记为完整兑现；
- 此笔只扣心愿钱包，不进入普通预算卡；
- 用户确认这是真实购买。

#### 3.1.5 本轮仍未锁定

- 卡片密度、配色、字号、材质和动效；
- 处理区折叠/展开的具体控件外形；

### 3.5 上一版页面方案（已废弃）

#### 首页

以下为 2026-08-01 旧样机方案。新 V1 首页以 3.1.1 为准：多卡固定顺序 + 顶部处理区 + 底部常驻 Agent，而不是单卡大号剩余、紧凑选择器或右下角 FAB。

首页首先回答当前在看哪条预算线、这段时间已经用了多少、还能花多少以及最近发生了什么。

当前基线使用：

- 横向预算钱包或卡片切换当前预算。
- 当前卡片停靠后同步更新分页、分类、日期和最近记录。
- 核心金额作为最高层级，预算名称、周期和摘要逐级后退。
- 当前预算摘要与相关分类、记录保持空间和数据连续。
- 一个明确的「记一笔」主操作。

横向切换、卡片、分页点和主操作外形都可以调整，但不能出现当前预算与下方数据不一致，也不能把同一工作流拆成难以理解的孤立区域。

2026-08-01 起，SwiftUI 首页先完成一轮视觉验证；同日根据首页的轻量方向，将这套注意力与表面语言扩展到当前 8 个核心页面：

- 使用一个紧凑的预算选择器替代横滑钱包卡，切换后核心金额、总支出和最近记录必须同步更新。
- 首页标题与预算选择器放在同一标题行，标题在左、当前预算在右；预算选择器不再挤占金额行。
- 金额区不显示「还能花」「可用」等解释标签，直接以大号当前剩余金额和紧随其后的小号浅灰「/ 预算总额」表达当前状态；当前剩余是全屏唯一强焦点。
- 首页金额以约 64pt、常规字重作为本次原生样机候选值；这是待模拟器与真机视觉验收的提案，不是永久 Token。
- 总支出放在最近记录标题右侧，以负数金额直接表达预算消耗，与下方消费记录建立对应；不增加圆形或胶囊底色，也不显示「已用」标签。
- 首页不显示当前日期和预算周期，避免在核心金额与最近记录之间增加低价值摘要行；日期继续保留在每条消费记录中帮助回看。
- 首页不再同时展示分类摘要与最近记录，保留最近记录作为“刚刚发生了什么”的主要明细；分类继续在预算详情和统计中完整呈现。
- 删除金额与最近记录之间重复的「记一笔」「预算」「统计」快捷区；预算与统计继续通过底部导航到达。
- 「记一笔」改为右下角悬浮主操作，固定在底部导航上方，不遮挡最近记录，也不占用中间内容空间。
- 最近记录集中到一个主要内容表面，记录行不再各自卡片化，也不依赖大量分隔线。
- 首页样机展示约 4-6 条虚构最近记录，用实际密度验证首屏疏密关系；数量不代表正式产品固定上限。
- 最近记录标题区不展示低价值的预算类型标签；样机数据没有真实时分时只展示日期，不制造虚假的时间精度。
- iPad 继续使用同一首页信息结构，但主体保持聚焦的阅读宽度，不把金额、摘要和最近记录横向拉满整个屏幕。
- 首页不固定展示装饰性的“线”或轨道；进度、临界和超出状态后续按真实状态单独验证，不在普通状态中抢占主焦点。
- 当前四 Tab 导航继续作为样机基线保留，本轮统一页面视觉和录入交互，不扩大为全局导航重构。

悬浮录入交互方案（2026-08-01，Native Prototype）：

- 轻点悬浮主按钮后，直接显示「文本」与「语音」两种录入方式；默认入口不再依赖长按，也不再通过一次性“探头”教授隐藏手势。
- 两个入口以主按钮为固定圆心，在其左侧与左上方沿同一圆弧半径展开，形成围绕主按钮的四分之一圆弧，而不是沿单一方向排成箭头。
- 主按钮在展开后成为明确的关闭入口；点空白区域、再次点击主按钮或选择录入方式都能收起。快速重复点击后的最终状态必须反映用户最后一次意图。
- 文本与语音都使用图标和可见短标签，不让颜色、位置或动效单独承担入口含义；辅助技术在展开后按任务顺序读取两个入口。
- 标准动效以主按钮为运动锚点，两个入口使用短距离、轻微错峰的弹簧展开和回收，强调灵敏、顺滑与适度弹性，不能让用户等待。开启「减弱动态效果」时，入口在最终位置淡入淡出，主按钮不旋转或缩放。
- 后续可以提供“轻点 `+` 直接进入上次或指定录入方式”的用户设置；本轮只记录为探索，不提前增加设置项或默认替用户决定。
- 语音入口只打开模拟浮窗，展示收听状态、波形、示例转写、取消和返回手动入口；不申请麦克风或语音权限，不连接服务，不写入消费数据，也不表示第二轮语音能力已经实现。
- 该探索只验证首页录入入口的可发现性、触达与动效节奏，不改变第一轮 MVP 仍只包含手动记一笔的正式范围。

核心页面轻量化统一（2026-08-01）：

- 首页、预算列表、预算详情、新建预算、文本记一笔、统计概览、消费日历、我的 / 设置共享同一注意力逻辑：每屏先回答一个主问题，再展开操作和明细。
- 页面主要依靠排版、对齐、留白与少量表面分组建立层级；一个区块只使用一层主要表面，不在卡片内继续堆卡片，也不把每一行单独卡片化。
- 大金额只用于真正以金额为主问题的页面；设置、列表和表单使用紧凑标题，不能机械复制首页的大数字。
- 中性画布、白色主要表面、深色主操作和低噪声辅助文字构成当前共享语言；状态色只表达真实状态或危险含义，不再把蓝色当作装饰性默认强调。
- 预算列表突出预算名称、剩余和必要状态；预算详情突出一条预算边界；统计突出当前预算的回看结论；设置保持安静、紧凑和可扫读；表单突出当前输入与完成动作。
- 底部导航、页面标题、预算上下文、列表行、主要按钮、选择状态、反馈与动效使用一致语义，但根据任务密度采用合适布局，不追求所有页面外形相同。

本轮重点验收单一焦点、疏密递进、中文排版、预算切换、录入入口和跨页面一致性。最终视觉与节奏仍由 Rex 在模拟器或真机确认。

#### 预算与预算详情

- 预算列表区分进行中、待结算和可回看的状态。
- 每个预算清楚显示名称、周期、已用、还能花或结算状态。
- 详情回答预算边界、当前状态、主要分类、最近记录和是否需要结算。
- 编辑、管理记录和删除预算容易找到，但危险操作不与日常主操作混淆。

删除交互遵循 `PRD.md` 的数据范围规则。共享记录默认保留其他预算归属，界面使用用户语言说明影响，不展示 binding、级联删除等实现术语。

#### 记一笔

当前流程：

1. 输入金额。
2. 选择一个或多个平等预算。
3. 选择分类。
4. 添加可选备注。
5. 确认记下。

当前上下文可以预选预算。切换预算或分类时保留金额和备注；键盘出现后，金额输入与主要操作仍然可用。保存后清楚呈现哪些预算发生变化，并为适合撤销的操作提供恢复机会。

“记下这笔”是当前按钮文案，不限制未来在不同上下文中使用同义且自然的表达。

#### 统计与消费记录日历

- 统计只服务预算边界和消费回看，不做复杂财务报表。
- 支持查看全部预算或单个预算。
- 展示月度概览、预算与实际、分类分析和消费记录日历。
- 筛选变化后，图表、日期标记和当天记录同步更新。
- 日期记录显示所属预算，避免多预算上下文丢失。

柱状图、环形图、日历控件和页面位置都属于设计方案，不是产品固定形式。

#### 我的 / 设置

- 展示当前预算摘要和中性的使用信息，不把少花或结余包装成成绩。
- 提供预算设置、记录管理、教程、隐私、反馈和版本等当前真实入口。
- 后续能力只有进入路线图阶段后才可以承诺可用；样机如预览 iCloud、导出或通知入口，必须明确标注为未来能力，不能伪装成已经实现。
- 当前使用清晰、可扫读的分组结构，具体容器形式可以调整。

#### 结算

- 展示预算总额、总支出、结余和预算周期。
- 存在共享消费时逐笔确认最终归属。
- 每个选择有明确选中态，完成前可以理解它会怎样影响相关预算。
- 进行中预算只预览结果，待结算预算才能正式完成结算。
- 当前版本不出现转到心愿。

结算反馈用于阶段性回看和确认，不将结余多少评价为成功或失败。

### 3.6 上一版共享组件语义

| 组件语义 | 必须保持一致的内容 | 当前表现 |
|---|---|---|
| 预算上下文 | 当前预算明确，多预算平等 | 钱包卡片、分页与选中边框 |
| 边界进度 | 计算口径一致，状态可理解 | 线性进度与金额 |

| 分类选择 | 当前分类清楚，切换不丢输入 | Pill / Picker |
| 记一笔入口 | 操作含义一致且容易发现 | 底部主按钮或工具栏入口 |
| 操作反馈 | 结果明确，可逆操作可恢复 | Toast、数字变化与触感 |
| 空状态 | 解释当前状态与下一步 | 标题、说明与行动入口 |

如果已有组件影响用户理解，可以重构或替换；不能因为代码已经抽象出来就成为设计负担。

### 4.3 极简参考图的设计哲学

本节整理 Rex 于 2026-07-31 提供的浅色金融 App 首页参考图。它用于长期校准 CheckLine 的注意力分配、信息密度和视觉秩序，不表示账户余额、转账、加钱等银行产品语义属于 CheckLine，也不表示白色、圆形按钮或某组固定尺寸已经成为当前方案。

这张参考图的核心不是“元素少”，而是严格管理一屏能够争夺注意力的内容：先用一个强焦点回答当前最重要的问题，再逐步展开上下文、操作和明细。它更接近“MUJI 式减法原则与现代数字产品排版的结合”，不是依赖米白色、细线或文具装饰营造风格。

#### 核心哲学：管理注意力，而不是填满空间

1. **一屏只有一个主角。** 核心数字或核心状态必须形成明显断层，其他标题、按钮和数据不能与它竞争。
2. **信息密度由疏到密。** 页面上部负责状态和理解，中部负责高频操作，下部才承载列表与细节；不要让用户进入页面就同时处理全部信息。
3. **留白承担分组。** 相关内容靠近，不同任务之间留下完整呼吸空间；留白不是等待填充的空位，也不应被解释性文案占满。
4. **层级优先由排版完成。** 字号、字重、灰度、对齐和间距先建立结构，边框、色块、卡片、标签和分隔线只在确有功能时出现。
5. **组件形状必须有职责。** 圆形用于紧凑图标操作，胶囊用于短小的上下文选择，较大的圆角表面用于真正需要整体承载的内容；不能为了统一视觉而让所有内容都卡片化。
6. **色彩保持低噪声。** 大面积使用中性表面和文字色，只让极少量高对比色承担主操作或关键语义；颜色不能成为装饰性分类系统。
7. **文案尊重用户理解。** 首页优先使用自然、短小的名词、动作和数据，不主动解释产品哲学，不用状态口号填补留白。
8. **重复建立节奏。** 同类操作保持一致尺寸和间距，同类记录保持稳定的图标、文本和金额对齐，使高密度内容仍然容易扫描。
9. **克制不是平均弱化。** 页面需要少量明确的视觉锚点；如果所有内容都同样浅、同样小或同样安静，反而会失去方向。
10. **产品哲学通过行为成立。** CheckLine 的“线”首先体现在用户定义边界、系统克制介入、临界时说清事实、越线后不作评价，以及有财务含义的决定由用户确认，而不是反复绘制线条或轨道。

#### 对 CheckLine 的继承边界

- 首页首先回答一个问题：“当前预算还能花多少？”预算名称、周期、已用和总额作为必要上下文逐级后退。
- 最近记录、分类和统计等详细内容应集中到清楚的后续区域，不在核心金额周围形成信息包围。
- “记一笔”保持一个明确主入口；同一屏避免再出现多个同级主按钮、悬浮操作和强调导航。
- 进度、临界和超出状态必须可理解，但不要求长期展示线形图案。任何进度线只有在提高理解效率时才出现，而且不能成为装饰母题。
- 多预算、关联账和结算仍需表达真实关系与用户决定权，不能为了视觉简化而隐藏金额归属或操作后果。
- 不继承总资产、账户余额、银行卡、加钱、转账或支付等真实资金心智；参考图只提供视觉组织方法。
- 不把浅色、黑白、圆形按钮或大数字机械复制到所有页面。具体表现仍需结合 CheckLine 的任务、状态、中文内容、iPhone 与 iPad 环境重新验证。
- 参考图没有呈现键盘、长文案、大金额、临界与超出、空状态、错误、文字缩放或 iPad 布局，这些场景不能从单张截图推断已经解决。

#### 后续设计评审问题

每次形成新的首页或核心页面方向时，优先检查：

1. 用户进入页面后，第一眼是否只有一个明确答案？
2. 页面是否形成“状态 -> 操作 -> 细节”的疏密递进，而不是从顶部开始堆满信息？
3. 是否有文字只是在解释界面、重复数据或填补留白，可以直接删除？
4. 信息层级能否主要依靠排版和间距成立，而不是依赖更多卡片、标签和分隔线？
5. 每种形状、颜色和强调是否都有稳定的产品职责？
6. 高频操作与记录列表是否通过重复和对齐形成可预测的节奏？
7. “Line”是否体现在产品如何对待边界和用户决定权，而不是浮于表面的视觉符号？
8. 简化之后，金额关系、预算归属、状态和操作后果是否仍然真实清楚？
9. 界面是否误导用户把 CheckLine 理解为银行账户、资产管理或传统记账产品？
10. 当前判断是否已经在真实中文内容、目标设备和关键状态中渲染验证，而不是只在理想静态稿中成立？
