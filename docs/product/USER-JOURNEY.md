# USER-JOURNEY — CheckLine 首个完整周期

> 这份旅程描述 V1 用户从第一次划线，到完成一次结算并理解心愿钱包的过程。时间以典型月度预算为例，一次性预算可按同样阶段运行。

---

## 一、用户起点

### 典型用户：小满

- 有想控制的具体支出，例如外卖、娱乐或一次旅行；
- 钱分散在 Apple Pay、银行卡、微信、支付宝和邮件账单；
- 不愿每天维护复杂分类表；
- 真正想知道的是“这张预算还剩多少”；
- 希望守住预算有正向用途，而不是只看到惩罚。

她第一次打开 CheckLine 时，不需要提供收入、债务或完整财务档案。

---

## 二、旅程总览

```text
Day 1               Day 1-3               Day 4-21              周期结束             之后
创建预算卡      →    获得第一批记录    →    查看与处理状态    →    检查并主动结算   →   心愿兑现/追溯修正
可选心愿/来源         Agent + 被动来源       风险与覆盖可见         钱包结果明确          下一周期继续
```

---

## 三、阶段旅程

### 阶段 1 · 创建第一张预算卡

| 维度 | 内容 |
|------|------|
| 触点 | 首次引导中的 Agent |
| 用户行动 | 说“这个月外卖控制在 800 元” |
| Agent 行动 | 整理名称、额度、币种、循环周期和必要归属规则 |
| 用户确认 | 确认第一张预算卡 |
| 用户理解 | “这张卡管外卖，不是我的真实账户余额” |

**Aha #1**：用户能用自己的语言划出第一条消费边界。

阻塞风险：Agent 如果替用户发明额度或把“日本旅行”误判成预算/心愿，会破坏理解。预算卡必须回答“管理什么支出”，心愿必须回答“结余想留给什么”。

### 阶段 2 · 可选补充心愿和数据来源

用户依次可以：

- 表达一个心愿，Agent 整理名称和参考金额；
- 配置 Apple Pay、银行短信或邮箱；
- 导入近期账单；
- 或全部跳过，直接进入首页。

**体验要求**：任何连接都不是门槛。设置页始终可以之后补连。

如果导入近期账单：

- 当前周期记录归入预算并立刻形成已用/剩余；
- 更早记录只帮助识别，不扣减当前周期；
- 重复来源自动合并，保留来源证据。

### 阶段 3 · 第一次看懂首页

首页首先展示：

1. 是否有待确认、未纳入、数据缺口或风险；
2. 固定顺序的预算卡状态；
3. 底部常驻 Agent 入口。

用户可以清楚分辨：

- 确认支出；
- 待确认金额；
- 预算剩余；
- 数据覆盖到什么时候。

**Aha #2**：用户看到的不只是一个漂亮余额，而是“当前数据有多可信”。

### 阶段 4 · 第一次主动记录

用户在首页底部说：“午饭 35，记到外卖。”

```text
常驻入口
→ 底部任务面板
→ Agent 识别结果
→ 信息明确时直接记下
→ 首页数字变化 + 提供撤销
```

若归属不确定，面板展示候选，由用户确认。调额度、删除或批量修改则必须展示影响后再执行。

**Aha #3**：简单消费不用填写表单，重要金额变化又不会被 Agent 静默执行。

### 阶段 5 · 被动记录逐步降低摩擦

Apple Pay、短信和邮件记录进入后：

- 系统标准化、去重和匹配预算卡；
- 高置信记录直接进入；
- 低置信记录显示待确认；
- 没有合理预算卡的消费进入未纳入区域；
- 首页显示各来源最后覆盖时间。

用户不需要每天处理所有记录，只在真正影响边界或结算时处理关键项。

**Moment of Truth #1**：被动来源是否减少操作，而不是制造一堆待办。

### 阶段 6 · 中段感知消费速度

对有明确周期/截止日期的预算：

- 系统结合已用金额、剩余时间和近期趋势；
- 解释“按当前速度可能提前几天用完”；
- 待确认金额只产生可能风险；
- 用户确认后才变成确定反馈。

无截止日期的一次性预算只看剩余额度，不制造时间焦虑。

**Moment of Truth #2**：用户是否因此调整下一次消费，而不是被提醒文案劝退。

### 阶段 7 · 周期到期但暂未结算

循环预算到期后：

- 旧周期进入待结算；
- 用户尚未结算时，新消费进入下周期队列；
- 新记录不会丢失，也不会混入旧周期。

一次性预算：

- 有截止日期时到期进入待结算，也可以提前或延期；
- 无截止日期时由用户在事情完成后主动结算。

### 阶段 8 · 检查并主动结算

结算页展示：

- 周期支出、预算额度和预估结果；
- 待确认交易；
- 各来源覆盖到何时；
- 可能缺失的数据；
- 对钱包和待恢复差额的影响。

用户处理关键项，或明确接受当前数据，再确认完成结算。

结果：

- 有结余：先补待恢复差额，再进入唯一心愿钱包；
- 越线：先扣心愿钱包，余额不足时形成待恢复差额；
- 循环卡开启新周期并接收队列记录；一次性卡归档。

**Aha #4**：预算结果不只是回看数字，而是进入下一轮行为的真实后果。

### 阶段 9 · 心愿兑现

用户钱包余额足够时，可以自由选择一个心愿，但点击“想买”不会提前扣款。

真实购买发生后：

1. Agent 识别疑似心愿交易，或用户手动选择“我已购买”；
2. 用户确认心愿和实际成交金额；
3. 钱包余额足够时扣除实际金额；
4. 该交易不再进入普通预算卡；
5. 心愿标记完成。

余额不足时不能完整兑现，避免制造不存在的资金。

**Aha #5**：心愿是守住边界后的选择权，不是另一个需要维护的资金账户。

### 阶段 10 · 迟到交易或退款

如果之后导入一笔属于旧周期的消费或退款：

- 系统定位原周期；
- 展示重算对结算、钱包和待恢复差额的影响；
- 用户确认后生成追溯修正；
- 不静默塞入当前周期。

这是长期信任的关键：历史可以修正，但不能悄悄变化。

## 四、关键体验节点

| 节点 | 用户应获得的确认 | 风险 |
|------|------------------|------|
| 第一张预算卡 | “这是我自己设的边界” | Agent 替用户决定 |
| 第一批记录 | “状态立刻有用了” | 空卡价值出现太慢 |
| 第一次待确认 | “AI 会问，不会装懂” | 错归类破坏信任 |
| 第一次边界提醒 | “我知道为什么提醒” | 黑箱、焦虑式文案 |
| 第一次结算 | “数据和后果由我确认” | 盲结算或强制对账 |
| 第一次钱包变化 | “只有一个清楚余额” | 多账户与重复计算 |
| 第一次心愿兑现 | “真实购买后才扣” | 预扣、重复扣预算 |
| 第一次追溯修正 | “历史变化可解释” | 静默改账 |

---

## 五、首个周期成功标准

首个完整周期后，用户应该能说：

> “我自己划了几条需要管理的消费边界。记录可以一句话完成，也能从我选择的数据来源补进来。我知道哪些数字是确定的、哪些还待确认。周期结束时，我确认结果，结余或越线会真实影响同一个心愿钱包。”

如果用户只能说“它帮我记了账”，说明 CheckLine 还没有兑现预算循环价值。

---

## 六、待交互设计验证

- 多张预算卡在首页一屏内如何保持可读；
- 顶部处理区怎样提示而不形成待办焦虑；
- Agent 底部面板在语音、图片、多步确认时的高度和反馈；
- 结算结果怎样既清楚又有阶段感；
- 钱包扣减与待恢复差额怎样温和但不模糊；
- 心愿兑现入口怎样避免被理解为购买推荐。
