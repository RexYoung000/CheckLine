# GLOSSARY — CheckLine 术语表

> 产品、设计、代码和文案必须使用同一套概念。金额含义不清时，以本表和 `PRODUCT.md` 为准。

---

## 一、产品与预算

### 预算线（CheckLine）

用户为自己设定的消费边界：线内自由，线外克制。不是复杂记账软件，也不是完整财务规划助手。

### 预算卡（Budget Card / `Budget`）

一条可结算的消费边界，包含用途、额度、基准币和周期。界面可使用卡片或预算钱包的视觉容器，但它不是真实账户。

**不要再使用**“主预算 / 副预算”“平等多预算同时扣减”等旧概念。

### 循环预算（Repeating Budget）

按每周、每月或自定义规则重复的预算卡。旧周期到期后等待用户主动结算，完成后才正式开启下一周期。

### 一次性预算（One-shot Budget）

只服务一次旅行、活动或其他具体事情的预算卡。截止日期可选；没有截止日期时由用户主动结束并结算。

### 预算周期（Budget Period）

一张预算卡在某一段时间内的独立运行实例。每个周期单独计算支出和结算结果。

### 下周期队列（Next-period Queue）

循环预算旧周期已到期但尚未结算时，用来暂存到期后新消费的队列。旧周期结算完成后，这些记录一次归入新周期。

## 二、消费与归属

### 记一笔（Capture an Expense）

通过 Agent 或其他入口记录消费。用户界面说“记一笔”，不说“录入流水”。

### 结算预算卡（Settlement Budget）

一笔消费唯一影响金额的预算卡。一笔消费最多有一张结算预算卡，也可以暂时未纳入预算。

**硬规则**：一笔消费不能同时扣减多张预算卡。

### 标签（Tag）

描述消费含义的非结算信息，例如餐饮、人情、聚会。标签可以有多个，但不额外扣减任何预算。

### 已确认归属（Confirmed Attribution）

消费信息和结算预算卡已经由高置信规则或用户确认，可作为确定金额参与状态和结算。

### 待确认金额（Pending Amount）

Agent 认为消费可能属于某张预算卡，但把握不足时暂时计入的金额。首页必须单独显示，只能触发“可能接近或越线”的提示。

### 未纳入预算（Unbudgeted）

消费不属于任何现有预算卡，或系统没有合理匹配时的明确状态。不能为了覆盖率强行归类。

### 预算归属覆盖（Budget Attribution Coverage）

当前已知消费中，已有结算预算卡归属和仍未纳入预算的金额/记录范围。它回答“预算状态覆盖了多少已知消费”，不同于数据来源覆盖。

### 匹配规则（Matching Rule）

用户纠正后由 Agent 提出的可读归属规则。系统可以建议应用到相似记录，但批量修改必须由用户确认。

### 来源证据（Source Evidence）

同一笔消费从 Apple Pay、短信、邮件或账单等来源出现时保留的原始来源线索。多个来源证据可以合并到同一消费记录。

### 跨来源去重（Cross-source Deduplication）

根据金额、时间、商家、卡片等证据判断多个来源是否为同一笔消费。高置信重复自动合并；不确定时由用户确认。

## 三、Agent 与数据来源

### 预算循环行动 Agent（Budget Loop Action Agent）

只处理预算循环相关行动：记账/改账、预算卡、状态查询、结算、追溯修正和心愿处理。它不是开放式个人财务顾问。

### 低风险直接执行（Low-risk Direct Action）

信息明确的单笔记录可直接写入，并立即提供撤销。

### 高影响确认（High-impact Confirmation）

调额度、改周期、删除、批量修改、结算、钱包扣减和历史追溯必须先展示影响，再由用户确认。

### 被动来源（Passive Source）

经用户首次配置后，能较少打扰地把交易交给 CheckLine 的入口。V1 包括 Apple Pay 系统自动化、银行短信系统自动化和邮件账单/小票。

“被动”不等于安装后无需配置，也不等于全渠道实时。

### 数据覆盖（Data Coverage）

某个来源当前是否已连接、最后同步/导入到什么时间、可能漏掉哪些消费。必须向用户清楚展示。

### 近期账单导入（Recent Statement Import）

用户主动导入微信、支付宝、银行或其他渠道近期账单的通用兜底方式。只有当前周期内的记录计入预算；更早数据只用于识别。

## 四、结算

### 待结算（Pending Settlement）

预算周期已经结束，但用户尚未确认结算的状态。到期不等于已结算。

### 检查式结算（Reviewed Settlement）

用户查看待确认交易、数据来源覆盖和可能缺失后，处理关键项或明确接受当前数据，再完成结算。

它不是强制逐笔对账，也不是系统自动盲结算。

### 结余（Surplus）

`预算额度 - 确认后的周期支出` 为正时的结果。结余先补待恢复差额，剩余部分进入心愿钱包。

### 越线金额（Overrun）

确认后的周期支出超过预算额度的部分。它先扣心愿钱包，钱包不足部分形成待恢复差额。

### 追溯修正（Retrospective Adjustment）

迟到交易或退款属于已结算周期时，在展示重算影响并获得用户确认后，对原结算和钱包账本进行的可追溯调整。

---

## 五、心愿

### 心愿钱包（Wish Wallet）

全局唯一的虚拟可用额度，代表用户守住自己设定预算后累积的净结果。

它不是真实资金账户，不证明用户整体财务上绝对安全可花。

### 待恢复差额（Recovery Gap）

心愿钱包已经扣到 0 后，仍未被覆盖的越线金额。未来任何预算结余都先补这个差额。

待恢复差额不是第二个钱包，而是同一钱包账本的负向结果。

### 心愿（Wish）

用户真实想获得的项目，记录名称、参考金额等必要信息。心愿不拥有独立资金余额。

### 心愿兑现（Wish Redemption）

用户确认真实购买后，按实际成交金额从心愿钱包扣除，并把心愿标记完成的动作。心愿购买不再进入普通预算卡。

### 目标价格（Target Price）

用户创建心愿时填写的参考金额。它不冻结钱包，也不是最终扣款额；最终按实际成交金额处理。

## 六、多币种

### 预算基准币（Budget Currency）

预算卡用于显示和结算的货币。

### 原币金额（Original Amount）

交易真实发生时的货币与金额，始终保留。

### 实际入账金额（Posted Amount）

银行最终记账的预算基准币金额，优先用于结算。

### 暂估金额（Estimated Amount）

交易尚未正式入账时，按标明来源和时间的汇率估算的金额。最终入账后更新同一笔记录，不新增一笔。

### 心愿钱包基准币（Wish Wallet Currency）

唯一心愿钱包用来汇总所有预算结算结果的那一种货币。全账本只有一个。

- 尚未产生钱包分录时，默认等于第一张预算卡的基准币，用户可以改。
- 已有钱包分录后，V1 不再更改。
- 不同币种的结余、越线或心愿金额必须先换成钱包基准币再加减。

### 钱包换算时点（Wallet Conversion Time）

用户确认结算、心愿兑现、退款或追溯调整的那一刻。到期、记一笔或导入不会写入钱包，也不会提前锁汇率。

### 换算快照（Conversion Snapshot）

一笔钱包分录当时使用的汇率、来源（实际入账 / 暂估）和时间。事后汇率变化不回写旧分录。

### 暂估汇率（Estimated Rate）

没有银行或来源实际入账汇率时，带上来源名称和时间的汇率。必须在确认页展示；不能作为静默事实。

## 七、废弃术语与规则

| 废弃项 | 新规则 |
|--------|--------|
| 一笔消费平等归属多个预算并各自扣减 | 一笔消费只有一张结算预算卡，其他含义用标签 |
| 关联账结算时决定“都算/只算某张” | 在日常归属阶段确定唯一结算预算，结算不做重复扣减 |
| 结余分别分配到多个心愿 | 所有结余进入唯一心愿钱包，用户自由兑现 |
| 重复型预算到期自动开始新周期 | 到期后等待主动结算，新消费进入下周期队列 |
| 心愿只属于后续版本 | 心愿钱包是当前完整核心循环的一部分 |
| Agent 自动替用户做财务规划 | Agent 只执行预算循环行动，金额由确定性规则计算 |
| “全自动同步” | 可选数据来源 + 明确覆盖范围 + 账单导入兜底 |

---

## 八、使用纪律

- 产品和设计先判断这是结算金额、标签，还是来源证据，不混用。
- 新金额概念必须先写入本文档再实现。
- 任何会改变预算、结算或钱包的动作，都要能说明来源、计算和用户确认状态。
- 用户界面文案仍遵循 `PRODUCT.md` 的温和原则，但不能因此隐藏真实金额后果。
